## 2. Performance: a measured lever in the generated code's contract

(The codegen experiment; the asm is in the roadmap's B6.) With the project's flags (`-fno-strict-aliasing` among them) LLVM must assume a store through `rdram` may alias `ctx->rN`, so after every MIPS store it reloads the registers it had in x86 registers. A four-instruction fill loop compiles to 6 x86 instructions with 4 memory operands per iteration at `XRC_GPR32`, 15 with 8 at 64 bits; with `restrict` on both parameters, 4 register-only instructions in both modes. Safe once `f_odd` is an in-struct array (the generator's only non-GEP access to the context, `tools/recomp/src/cgenerator.cpp:96-98`; nothing takes a field's address). Plan: roadmap B6. Related, found by the build audit: `xrc_pbkit` is compiled with no `-O` at all in the default build (`xbox/CMakeLists.txt:41`: only `-w`; the hw target has `-O2` at :74), so pbkit's push helpers run unoptimised on every draw; add `-O2`.

## 3. The PC side: security and robustness

From the PC review (`tools/n64rx`, the build scripts, `tools/xbox`, the
Docker files, `app/`, the workflows), the supply-chain inventory and the
learn and Yaz0 audit, de-duplicated. Checked and found sound, so not
listed: every subprocess takes an argument list (no `shell=True`,
`os.system`, `eval` or `exec`); the XBE title reaches cxbe as one argv
element `-TITLE:<title>`, and the allowlist leaves nothing special for sh,
MSYS bash or cmd.exe (tested on a CMake+Ninja mock); no ROM-derived text
reaches TOML, C identifiers or compiler flags (`func_%08X`, fixed libultra
names, every `-D` a formatted integer; `c_str` escapes quotes and
backslashes); FTP names are fixed or matched by an anchored regex, ftplib
refuses CR/LF, and the app passes the password in the environment, never
in argv or the log; the app runs with `contextIsolation`, `sandbox` and no
`nodeIntegration`, a CSP of `default-src 'none'` with no inline script,
navigation, new windows and permission requests denied, `app://`
contained (13 hostile URLs tried), about thirty named preload entries with
`event.sender` checked, every ROM-derived string through `textContent`;
`toolchain.js` checks the hash before it unpacks (tested with a fake
archive) and its zip path refuses traversal and symlinks; the npm lock has
sha512 integrity for all 300 packages; none of the 1,295 history blobs
holds an N64 header word or an XBE, and the tree holds no secret.

Checked and found sound: the per-thread events are auto-reset and sticky,
and every consumer loops on its own predicate (spurious wake-ups only,
none lost); the message queue against libultra's algorithm (200 random
rounds of 60 operations on 1-6 slots, 0 differences); the event table, the
held done events and the retrace flush; `ai.c`'s sample arithmetic and
`osAiSetFrequency`'s rounding; `time.c`'s conversions and wrap; the PIF
parser's bounds; both pak CRCs (246 checks), the bounded inode chains, the
save devices' masks, the atomic write; the interpreter's unaligned loads
and stores (4,000 random cases, both widths), branch-likely, division by
zero; `jpeg.c`'s bounds. Divergences that match upstream and are
documented: `c.cond` ignores NaN, `round.w` rounds half away from zero,
`sc` always succeeds.

The reviewer's note on a libultra-exact scheduler agrees with the
roadmap's B1 and adds: the async sources (VI, SP/DP, AI, PI, SI, timers)
delivered as pending interrupts on the token holder's own thread at safe
points, and only with interrupts on; "interrupts off" as "no hand-off"
rather than a lock and a boost; a message waking only the first waiter by
priority then FIFO (today `wake_all`, `thread.c:207-211, 709, 770`). The
race classes the present design cannot close: threads of different N64
priority on one kernel level interleave; NT's wait boost runs a woken
thread ahead of an equal one; a thread blocked on a host primitive lets
lower levels run; priority inversion on every host lock; thread-record
transitions without a lock (an `osStartThread` between `thread.c:494` and
`:266` is lost); done-event order by heuristics; `osYieldThread` as
`SwitchToThread`. On the interpreter's decode cache (roadmap B6): about
9 ns (19 cycles) per interpreted instruction on the host x86-64, two to
four times the cycles expected on the P3; key it by physical page and a
generation, and invalidate from PI DMA (after 5b.23), `osInvalICache`, the
`cache` instruction (a no-op today, `interp.c:502`), `xrc_tlb_write` and
the guard.

Performance (not measured): `wake_all` signals while `xu_send` still holds
the lock, about three context switches per cross-thread wake instead of
one (`thread.c:709-710, 770-771`); `__osEnqueueAndYield` is a `Sleep(1)`
poll, 1-2 ms per message hop for unnamed libultra (`more2.c:22-26`);
interrupts off and on cost four kernel priority calls and a
critical-section pair (2.4); each retrace runs a flush scan,
`xu_ai_tick`'s 64-bit divide and the guard's retrace hook; the audio
volume costs two integer divides per frame (`audio.c:309`); PI DMA
translates per word (about 5 ms per MB on the P3, an estimate).

## 9. What this review did not cover

  memory-pressure and GPU-ordering statement here comes from code or a host
  run, and the performance items are "not measured" unless they say so.

  ROMs and hand-written MIPS words; `test_analyze` checked 0 pairs.

  stood in for the host tests and the codegen experiments (B6's numbers
  are clang 18's); `test_splash` (it needs nxdk) did not run.

  reads only (5c, 5d), not line by line; the `nv2a_cc.c` combiner
  cross-check was lost and must be redone.
- The audio HLE (`asp_hle.c`) was read but not reviewed in depth.
- Also out of reach here: Windows-specific paths (device names,
  `n64rx.cmd`'s `%*`), node-tar, yauzl and the npm install scripts (no
  `node_modules`), GitHub-side settings (the default token rights, cache
